# 重用與既有機制

由 [arch-thinking](SKILL.md) 的觸發表載入。產出候選與可否共用的理由，呈現交消費命令。

## 先查既有同類機制

新增注入／fallback／provider／reader 前，查定義處、實際消費端慣例、模組 AGENTS.md 的設計宣稱。文件與實作不一致時標明差異；不可只讀定義便宣稱沒有既有介面。找到既有機制後，比較它是否滿足本次 use case，再決定擴充或新增。

## Pattern Radar：候選不等於可共用

1. **找候選**：enum 比名稱和值；function 比責任、簽名與呼叫關係；data structure 比欄位與使用方式。查詢工具依 [symbol-query-routing](../../rules/symbol-query-routing.md)。名稱／欄位相似度只用於排序查證，不是設計信心，也不以未校準加權分數決定重用。
2. **判語義相容**：逐個候選核對概念含義、invariant、authority／ownership、生命週期與改變理由。同欄位而語義或修改責任不同，保留各自模型；必要時用明確轉換銜接。
3. **判放置成本**：抽取後誰依賴誰？是否使 lean 廣用模組承擔 heavy 實作？是否跨 context 暴露內部型別？對所有已識別消費者比較，而非只看新 caller。
4. **給結果**：可共用／保留分離／待查證，附具體理由與證據缺口。候選存在不等於必須重構；不把 scope 外整理塞入本次修復。
5. **落地後複核**：抽 helper 或搬 symbol 後重查落點、依賴方向及消費者，確認抽取沒有製造新的成本或契約差異。

校準例：兩個 context 的 amount 一個指應收金額、一個指申報價值，欄位與 enum 相同仍不足以合併；同一契約的純換算在多處重複，才進一步查證能否抽共用。
