五個問題

① 工作從哪來？✅

想法先落 draft／pending 區；一旦承諾，才由 board（Backlog.md kanban）建卡並配置 id。board 就是 control plane，卡是所有 downstream（status、refs、驗收）的錨。
現況：board 運轉中；single-writer 化 ⚠️ 大致落地（09-16 AIR-72——config 切 true＋kanban 條款＋mkdir lock；見 04）。

② 在哪做？⚠️

target：primary 只管 board state；寫碼改文檔進該卡的 persistent worktree；免卡小修走 ephemeral WT。
現況：wt-open／wt-close helper ✅ 已落地（09-16 AIR-72）——走 WT 的卡進 persistent WT，未走 WT 的卡仍照現行 git 慣例（雙軌並存、同卡禁混用；見 03）。

③ 誰能寫什麼？⚠️

按「這份 state 的唯一 writer 是誰」分：board metadata 只有 primary 能寫；code／rules／skills／docs 只有該卡 WT 能寫；顧問與 audit 唯讀。
現況：card WT ⚠️ 已落地（雙軌）、ephemeral ✅；顧問／唯讀環境 ⚠️ 現有做法可支撐、未機械化（見 03）。

④ 如何收？✅

validate → review → commit → owning line 吸收（必要時 rebase，一律 ff-only）→ finalization → 移除 WT；顧問產出也要有收法，不許丟著等它自己回來。
現況：收斂 git 紀律 ✅ 現行不變；wt-close helper ✅ 已落地（真卡收線已驗——AIR-77；receipt 每次執行自動落盤 .git/wt-close.log——AIR-112；見 05）。

⑤ 機器壞了怎麼回來？⚠️

六段 runbook：工具鏈 → rules/skills 部署 → hooks 接線 → 記憶池恢復 → cron/launchd 重建 → code-reality。缺可靠 source 的步驟停在缺口，不拼假 runbook。
現況：code-reality ✅、工具鏈 ❌、其餘 ⚠️（見 06）。

User Story ①——多 session 共享 WT 打架

身為同時開著多個 session 的人，我希望別的 session 不會把我腳下的 branch 拉走。

❌ 實際痛點（真實事故）

多個 session 共享同一個 primary checkout——一個 session 做 git checkout 切 branch，其他 session 的 cwd／branch 當場被換掉。WT workflow 裁決報告背景記載「checkout 中途被切」，同型故障還有 relay 過時×6、外卡落錯 branch×3；workflow.md 的結論：「因共享單一 checkout，所以同 repo card session 絕不能並存」。

✅ 採用架構

1 card = 1 branch = 1 persistent worktree：branch 承載工作生命週期，WT path 承載穩定執行位置；同卡跨 session 重用同一 WT；writer 與 reviewer 指向同一份工作狀態（共用 identity＝可共讀、按流程串行寫）。

Care（為什麼要管）

branch／cwd 是 session 的隱形地基，被別人動了，「我以為我在哪」的全部假設失效——這是 ③開工站斷點最多的根因。

為什麼 board 只能有一個 writer？

board 的 runtime metadata（task id、status、refs、final summary）如果有多個 writer，id 撞號與狀態互踩只是時間問題。
User Story ②——開卡撞號兩次

身為同時推進多張卡的人，我希望每次建卡拿到的 id 唯一，不用事後清場。

❌ 實際痛點（真實事故）

卡撞號×2——WT workflow 裁決報告背景記載的實際事故。根因：多 WT repo 各自掃描 id，其他 branch 的 committed 卡與 working-copy 裡未提交的卡互相看不到；backlog/config.yml 至今仍是 check_active_branches: false（已實核）。

✅ 採用架構

board single-writer：board state 唯一 working copy＝primary 的 backlog/tasks/*.md；backlog/tasks runtime metadata 只有 control plane 是 writer；card WT 不直接執行會改 card runtime state 的 backlog task edit/create/complete；check_active_branches: true 做跨 branch discovery；建卡保留跨 WT filesystem max-id 預掃，補 untracked／staged 卡的盲區；id／status／ref／finalization 經 control-plane helper 在 repo-local lock 下執行。

Care（為什麼要管）

id 是卡的機械身份。撞號之後「哪張卡是真相」變成考古題，board 的全部下游（status、refs、precheck、Capabilities 結算）跟著錯。

Status / Source

⚠️ 大致落地（09-16 AIR-72：check_active_branches: true＋kanban board single-writer 條款＋開收 mkdir lock；card WT 內禁 task edit 尚為語義條款、非機械 enforcement）——workflow.md「Board single-writer」節；事故記載：ai-analysis/reports/2026-09-10-wt-workflow-decision.md 背景。

為什麼打開 config flag 不夠

  • check_active_branches 只解 cross-branch discovery：讓多 WT repo 看得見其他 branch 已 commit 的卡。
  • working-copy 裡的 local card 仍可能遮住其他 branch 的同 id 狀態——flag 取代不了 single-writer ownership。
  • untracked／staged 的建卡 flag 看不到——所以 max-id 預掃要保留，兩層各補一塊盲區。
control-plane metadata commit 授權（user 09-11 裁定）：建卡＋開工 metadata 特赦、結案兩步走條件鏈（precheck 綠＋結算物同 commit）——單一源＝outward-action-consent「Commit 專屬段」。

做完怎麼收？

收斂序列沿用既有 git 紀律——WT target 改的是 working-directory ownership，不改 trunk-based convergence。finalization 不先於 convergence。
  1. execution plane 內完成工作：work → validate → review → 修正 → commit（commit consent 不因 WT helper 自動失效）。
  2. wt-close preflight：重取 control-plane lock，驗 WT／branch identity、working tree 無未處理變更、commits 與 scope 相符、owning line 新變更未使 baseline 假設失效。
  3. owning line 吸收：owning line 沒前進 → ff-only candidate；已前進 → rebase working branch onto owning line → 再 ff-only absorb；ff-only 仍失敗 → 停下查原因。
  4. finalization：git convergence 成功後，primary control plane 才 status → Done、寫 final summary、完成態 refs、Capabilities／metadata 結算、值得保存的事實按 memory-audit 蒸餾。
  5. 移除 execution plane：刪 card WT、刪已被完整吸收的 branch、git worktree list＋ancestry 最終確認、釋放 lock。
  • helper 已落地（09-16 AIR-72）：scripts/wt-open.sh 試點通過、scripts/wt-close.sh --preflight pipe-test 驗證（真卡收線已驗——AIR-77；receipt 每次執行自動落盤 .git/wt-close.log——AIR-112）；未走 WT 的卡沿用既有 git 紀律收斂。
  • 鐵律：trunk／owning line 不被 rebase、不 force；不以 merge commit 迴避 ff-only 失敗。
  • 任一步失敗都要保留可判斷的 branch／WT／control state；不得靠刪 WT 製造表面完成。
  • board Done 表示工作已被 owning line 接收——不先於 convergence。
  • relay freshness 不因 WT 化免除：relay 是接手說明不是 repository truth；card baseline 對 current owning line／HEAD 的比對照做，baseline 後有新 commit 先判是否碰 scope。
User Story ③——顧問結果要有收法

身為派出顧問（external runtime）的 caller，我希望顧問的產出有明確收法，不會停在背景工作裡沒人認領。

❌ 實際痛點

（保守敘述——本卡的事實源不在 blueprint 四檔內，收法記載於 WT workflow 裁決報告）顧問產出走 bridge 背景工作、落到暫存輸出檔；caller 必須主動收回（wait／認領）並固化，產出不會自己進入決策流。裁決報告即一次收回實例：雙顧問全文經 .agent-tmp/bridge-{muse,codex}-wt-out.txt 收回後固化進裁決。

✅ 採用架構

顧問結果收回是 caller 的收斂責任：背景工作掛 wait、產出落 repo 內暫存區（禁 /tmp）、由 caller 認領並固化進 report／blueprint；「做完怎麼收」的序列裡沒有「丟著等它自己回來」這一步。唯讀／顧問 session 的執行環境依 03 節 routing（read-only checkout 或 ephemeral WT）。

Care（為什麼要管）

收斂站的鐵律是每份產出都有唯一收斂路徑；顧問產出若無收法，⑥收斂出現斷鏈——做了研究、下了決策依據卻消失。

Status / Source

機器壞了怎麼回來？

從「硬碟壞掉、只剩 repo 與外部備份」重建的六段 runbook。標記語義：✅ repo 已有可依循的現行 source／⚠️ 核心形態有源但缺 setup 或 recovery pointer／❌ 沒有足以可靠重建的 source。缺可靠 source 的步驟停在缺口，不從舊機現況或歷史 report 拼假 runbook。
User Story ④——硬碟壞了重建

身為這套系統唯一的擁有者，我希望硬碟壞了之後，靠 repo 加外部備份能把工作環境重建回來。

❌ 實際痛點

一般 git clone 帶不回的東西比想像多：memory pool 是 local-only Git state（只複製 markdown 不算恢復）；ZCode cron prompt 在 local DB、repo 無 verbatim 重建源；Claude settings 含 secret 不入版控。「目前這台機器上已經有」本身不是 fresh-machine recovery 證據。

✅ 採用架構

六段 runbook（下圖順序即依賴順序），每段明列現有支撐與缺口；prerequisite probe 任一缺失即停止 runbook，不反推安裝命令。

Care（為什麼要管）

八站的⑧運維就是這一節：狀態外部化只對「可重建的狀態」成立——runbook 的 ✅ 只給「可從 source 重建並驗證」的面。

Status / Source

User Story ⑤——預覽搶埠連環事故

身為多 session 作業的人，我希望看產物不需要搶埠，也不會殺到別人的預覽。

❌ 實際痛點（真實事故）

舊殭屍 http.server 佔 8765 擋住進行中 session 綁埠；第三個 session 誤判殭屍砍掉後，活 session 隨即搶到 8765——臨時 server 無埠治理、無生命週期，活過 VSCode、活過 session 跨 session 佔埠，撞埠與殭屍是必然不是偶然。

✅ 採用架構

臨時 server 全面淘汰：session 交付改「給路徑」（user 點開）或 :6421 URL（deep link）；日常預覽零 server（內建瀏覽器 file: 直載）；唯一常駐＝:6421（stable 契約）。曾評估的替代案——:6421 擴 route 到 repo 根、route carrier 中立化、新專案 viewport runbook——「路徑即可點開」成立後全部取消。

命令為誰服務？（Priority backbone）

09-12 拍板的多卡優先序治理——commands 不是按生命週期階段（EP / code）分，是按產出受眾分。設計、審查、討論任何命令時，先問「這命令的產出給誰消費」。

受眾二分：兩軌道平行不交匯

軌道消費者產出形式誰推動
① LLM 執行鏈機器自讀自判自修工程化、self-contained（EP、findings、code）AI 自主（人類開頭觸發）
② 人類 viewport人類用「大原則」判讀意圖（行為 artifact＋認知誤差點）＋結構（whole-picture 心智模型）人類切入（或 AI 產出、人類讀）
單檔單受眾：一檔兩受眾必然產生 token 牆——/ep-review、/code-review、/audit-test、/implement 內部審查、/judge-review 屬軌道①；/debrief（改動理解）、/illustrate（結構 viewport）、/smell-detector（壞味道）是軌道②。本頁即軌道②的產物。

原理：人補 LLM 的結構性 blind spot（direction >> quality）

LLM blind spot失敗人類互補認知命令
缺 whole picture → 重造既有重造 enum／模組整體直覺（細節忘但感覺得到關係／重用）/illustrate（結構 viewport）
抓不準意圖 → 偏方向漂亮但錯方向持有 vision，判「這是我要的嗎」/debrief

優先級：方向 >> 品質。LLM 預期能做到 Clean Code 等級（頂多需人提點）；災難性、無法靠 polish 彌補的是方向錯。所以 viewport 重度傾斜在方向驗證，不浪費人注意力在 code 品質（那是 /code-review＋LLM 自身能力的事）。viewport 渲染的是人類用來承載意圖／理解結構的 artifact（use case／scenario／UI／範例／心智模型），不是 code 結構。

規範正典不複製：三層介入表與核心流程命令分類表（含工具／維護命令歸類）的正典住 root AGENTS.md「命令的受眾視角」節——本頁不複製（殼不裝治理規則複本，本站殼頭宣言）。upstream 變更由 projection freshness gate 追蹤（manifest）。
