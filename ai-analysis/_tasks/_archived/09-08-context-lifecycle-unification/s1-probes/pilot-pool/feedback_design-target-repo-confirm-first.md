跨 repo 生態的規則／工作流設計，動手前先確認**主場 repo 與真實驅動 pain point**——抽象分析可以全對但打錯戰場；雙家族（AI＋muse）共識防「分析錯」，防不了「戰場錯」。

**Why**（09-08 卡 branch 弧實證）：AI 與 muse 雙家族同向得出「ai-rules 輕量採納、mosaic 不採納」的完整建議（失敗模式分析全成立），對話末端 user 揭露「這設計主要是為了 mosaic 啊」——真實需求是三個 VSCode 視窗（＝三 WT）的 ambient 顯示。目標場是 user 腦中的工作形態，不是分析者推斷的合理場景；需求的載體線索常已在 user 用詞裡（user 問命名時想的已是 war-77 線縮寫形態）。

**How to apply**：
- 多 repo 設計討論第一輪就問「主要想解決哪個 repo 的什麼痛」，並從用詞線索驗證目標場假設
- 「branch 顯示＝harness 恆渲染的唯一 git ambient UI」是獨立價值軸——純 git 機械軸分析（branch=重複索引）會漏掉它；tag／commit-id 替代品在顯示軸不等價
- 反向建議被需求反轉推翻時：重跑設計而非辯護舊結論；讓原反對者（muse）逐項對照自己論點哪些被新機制化解——「反轉對照」是有效的審查 prompt 必答段
