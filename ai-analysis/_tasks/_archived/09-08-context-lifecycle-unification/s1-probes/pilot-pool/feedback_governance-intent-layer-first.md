user 的治理訴求可在多層落地（下游補救／機械攔截／規範／上游認知動作），user 意指的層次≠我先想到的層次——偏靶的快速響應看似積極，實則多耗往返。實證（2026-09-06，memory 廢話治理）：「指導寫入不要這麼多廢話」我三輪才對準——①下游 cluster merge/audit 效率（被拉回「寫入當下」）②hook 3K 閘＋body 形態規範（被拉回「寫入前想」）③一句話測試＝認知動作層才收（終態見 [[feedback_inflow-needs-outflow]]）。

**Why**：機械閘攔「太長」攔不住「無腦」（2.9K 流水照樣過閘——閘不檢查想過沒）；規範管「格式」不管「想清楚沒」。層次錯配時每輪落地都完整可用，但都不是 user 要的那層——三連校正成本遠高於開口問一句。

**How to apply**：治理/行為類訴求動手前先自問「這訴求的目標層次」（改流程？改規範？改工具？改思考動作？），有不確定就一句話跟 user 確認層次再動手；機械閘與規範可作縱深，但不能拿縱深代替 user 指的那層。與 [[uc-inventory-before-structure-proposal]]（提案前先盤點）同族——都是「動手前先對齊 user 心中的對象層次」。

姊妹實證（2026-09-07，user 糾正「你不要啥都加上 memory」）：行為出問題（context 太大跳過收尾鏈）時，我寫了新 memory 條目修品行為——但規則（guide 銜接機制＋post-build skill）與既有 memory（consistency-gate / review-even-on-quick-fix）都已覆蓋。**行為漂移的第一響應層是「既有規範執行了嗎」，不是「新增載體」**；寫新 memory 前雙查：rules/skill 條文已有＋同主題 memory 已有（增量併一句錨，不建新檔）。
