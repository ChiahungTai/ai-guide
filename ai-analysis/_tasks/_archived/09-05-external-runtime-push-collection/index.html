問題與解法

為什麼現在的委派收法在燒 request——以及 push 化怎麼消掉它
LLM 層輪詢成本
N × request

每輪檢查＝1+ LLM invocation 且全 context 重送；30 分鐘 job 每 3 分鐘查 ≈ 10 request

push 收法成本
1 × request

背景 Bash 掛 bridge 阻塞呼叫，exit 自動喚醒——等待期 0 request、完成時恰好 1 個

bridge 內部輪詢
0 request

muse wait 以 500ms 輪詢 ledger——純 Node process，零 LLM 成本、亞秒偵測

  • 現行收法在 LLM 層輪詢：agents/AGENTS.md 記載 muse＝「背景 Bash＋jobs.json 輪詢（rg＋ps）」、codex＝「wrapper＋resume-to-poll」
  • wrapper≠job 錯位是實證：AIR-13 弧 muse×2＋codex×2 均需人工介入收斂；wrapper Bash 另有 10 分鐘上限（因果未證，僅標註）
  • 三家阻塞能力已齊：muse wait（bridge 0.2.4 已落地）、codex status --wait、grok runs --wait——不需動 upstream

收法決策樹

四種形態各走各的路——LLM 層永遠只做「等喚醒」
收法決策樹（mermaid——LR 單向通道＋多站鑽石決策、無互動導航需求）↗ 全屏
形態收法備註
簡單轉發（review／critique／diagnosis）主 session 背景 Bash 直呼 bridge task（阻塞形）→ exit 喚醒 → stdout 即 finalTextjobId 照記（reviewer 交接契約不變）
長跑 >10min同上——背景 Bash 無前景 10min 限制；或兩段式 --background 拿 jobId → 背景 Bash 掛 wait（muse wait --timeout 0：裸 wait 預設 5min 到期＝exit 124、0＝forever；codex status --wait --json：預設 4min 到期＝正常 exit 0＋waitTimedOut:true 旗標——無 0=forever，--timeout-ms 0 靜默回落 4min，只能顯式大值）唯一未實證前提＝致命 POC（build 前必跑）
prompt 工程（codex）wrapper 內單次阻塞 task＋env fallback 預寫wrapper Bash 10min 上限；預期超時改走直呼
fallback（罕見：背景 Bash 不可掛）ETA-gate：推估完成前零檢查 → 屆時單查 → 重掛遞減 timeout 的阻塞 wait階梯緊化由 timeout 遞減達成——永不做 LLM 層定時輪詢
codex env 假完成判 job 未建立 → 重派新 agent非輪詢、非雙跑
已決策勿重辯：push 優先（user 09-05 裁定）｜bridge 端 ETA 階梯輪詢 YAGNI（wait 已 500ms、bridge 輪詢零 LLM 成本；但 timeout 形狀要管——muse 長跑帶 --timeout 0（0＝forever）；codex 無 0=forever，timeout 到期＝exit 0＋waitTimedOut 旗標）｜codex／grok upstream 不改｜S2 降級＝範本預載＋落差記錄（ZCode 事件子集無 SessionEnd——repo 定案）｜user 階梯設計以 LLM 層 fallback 紀律（ETA-gate）形式吸收
