為什麼要改

同一條 coding workflow 內，其實包含不同能力與權限的工作
  • 判斷密集：EP synthesis、judge、重大架構裁決，需要已實驗合格的 decision-grade model。
  • 執行密集：有 accepted EP 後的 implement、查詢與機械驗證，可交給 execution-grade model。
  • 能力正交：原生影像能力不是一般推理強弱的別名；GLM Flash 可在 visual observation 上優於 GLM 5.3。
  • 狀態會變：provider、carrier、quota 與 Coding Plan 會改變，不能寫死在穩定 model doctrine。
目標是讓使用者只啟動既有 workflow；每個 phase 自動產生需求，再選符合需求的 model binding。

新的責任邊界 S1–S4 已實作

把供給、需求、部署與即時狀態分開，避免不同變更原因互相污染
Workflow owns demand

每個 phase 產生 WorkUnitContract：Role、authority、qualification、judgment、capabilities、surface、independence、escalation。

Catalog owns supply

ModelIdentity、DispatchBinding、effective effort、qualification status 與 evidence source；不放 Role、quota 或 preset。

Preset owns deployment

Registry slug 的 tools、sandbox、background 與 default binding；subagent 是執行 instance，不是 Role。

Snapshot owns availability

個人方案、quota、reset、available／unavailable／unknown 在 dispatch 當下形成，來源在 memory／runtime probe。

概念回答的問題禁止吸收
Role這個工作負什麼責任、能做什麼裁決？model、provider、carrier
Candidate哪個 model identity＋binding＋effective effort 真正合格？workflow phase、即時 quota
Resolver protocol如何 hard-filter、檢查相容性、處理 override 並形成 DispatchPlan？workflow ownership、部署 projection
Marshal responsibility何時推進、重試、升級、停止？model 選擇、findings 裁決
架構圖待結案弧裝入
本階段刻意不產渲染管線圖。實作與 post-build 收斂後，才依終態產生正式視圖，避免計畫圖在架構修正後失真。

使用者工作流程

原本的命令入口保持不變；系統在每個 consequential dispatch 前解析一次
工作預設能力要求升級／停止條件
execution-planevidence 可 execution；全域 synthesis 與 finding 裁決為 decision無 decision-qualified candidate 時 fail loud
implementaccepted EP 後可 execution＋applyEP 衝突、新 invariant、公開邊界、反覆失敗時停止本腿並升 decision
judge-reviewArbiter＋adjudication＋decision＋final disposition弱 seat 必須外派；不得自行降級裁決
post-buildReviewer、Arbiter、fix、verification 各自解析權限固定；更強 model 不會讓 Reviewer 取得 apply／final disposition

高推理＋影像的兩段式 fallback

1. Visual observer

visual-qualified model 取得原圖，輸出 source identity、區域、facts／interpretations、不確定項與 delivery receipt。

2. Decision Arbiter

decision-grade model 只裁決 observation artifact；必標 arbiter_viewed_source=false 與 decomposed-not-equivalent。

模型有 native_vision 還不夠；所選 DispatchBinding 也必須能把 image 傳入。只有 dispatcher receipt 能證明 Arbiter 真的看過原圖。
