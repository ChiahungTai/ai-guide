為什麼・架構總覽

動機鏈：muse 導入 → 三臭皮匠獨立調查 → 統一架構定案 → 用自己完成自己
  • 起點：muse spark 已是主力實作 model（GLM=規劃審查、muse=實作、codex=診斷），但三家族分工沒有 routing 真相源——派誰、怎麼派、怎麼收、誰驗收，全靠即興。

Dispatch 形態轉移・量測

build 期撞到的 transport 問題，當場蒸餾成架構（B-1/B-2）

本弧前半段 wrapper agent（muse-rescue／codex-rescue）連續四在 runtime 未終局時提前收工、codex 又遇 CLAUDE_PLUGIN_ROOT 為空導致 job 未建立——三種失敗模式對應三種完全相反的處置，不能靠即興判斷。

① transport 未啟動

env/module 錯誤、log MODULE_NOT_FOUND、jobs.json 無該 job → 可安全重派

② 在跑・wrapper 已收

jobs.json running、ps 進程在 → poll 收集，禁重派（重派＝雙跑）

③ 死中途・wrapper 空轉

進程已亡、jobs.json 停滯 → 機械驗收＋TaskStop

形態轉移實證（B-1）

  • WO-1（wrapper 形態）：需 1 次 resume-to-poll 介入
  • WO-2/3/4（主 session 直呼 bridge CLI＋背景 Bash＋jobs.json 輪詢）：零介入，完成通知直達
  • muse 委派預設形態改為直呼；wrapper 降為別名——從源頭消除生命週期錯位

首批量測（擴大委派的依據）

額度面：build 級工單各吃訂閱 5h 窗口數個百分點——4 發工單＋6 次審查 agent 同日完成，窗口健康。context 面：4 次手術全在 muse/reviewer runtime context 消化，主 session 只收報告。
