讓你跟得上重要設計

承接已完成的 Marshal；這一弧設計流程如何使用它。
  • 目前的主要成本是同一份工作在不同入口重複判定、審查、讀料與結算。新提案保留既有命令，讓它們使用一致的風險判準與證據身份。

    方向 brief 先說你將得到什麼；成果 brief 再說真的改了什麼、如何驗證、哪些仍不確定。你仍決定 compact 時機及 commit/deploy 授權。

四段改造，沿用既有命令

以下均為計畫中，尚未修改現行規則。
  • S1 統一 review 風險與證據身份 → S2 接回規劃、實作與收斂入口 → S3 先落盤、恢復後核對 → S4 精簡視圖與結算，完成 behavior pilot。
流程示意・計畫中
規劃 → 獨立 review → accepted EP → 實作與驗證 → 補未覆蓋 review → 裁決及修正 → 成果 brief → user commit
中斷時先 checkpoint；恢復先查實物、背景工作與 active findings，再做下一步。圖形渲染待後續 hook 2 評估。
情境新提案保留的防線
一般變更一個獨立 reviewer；普通中間段以實跑與證據為主需求、正確性、驗證 profile 與弧末 review
公開邊界、風控、安全、控制面 gate分離 fresh／intent，補必要專項與段級 review不能因 diff 小或 quota 少降級
整合器、新簽名或注入點保留 adversarial／architecture／consumer 專項原有 extra 不因 base 減量消失；UC-split 亦保留
不跑 post-buildfallback 仍先核對弧級 review；缺失先補若明示停審，僅交 Built／🟡，不報完成
已審內容再次收斂核對 scope／content／profile 後復用，只補 delta缺身份就全審；跨段整合仍驗
usage 中斷先保存下一步與未決證據，memory 整理可另交接不自動 compact；不把 Built 當 Verified
驗收先看 seeded 反例能否守住，再看重複派工與讀料是否下降。沒有量測，不宣稱節省比例。

主要風險

  • 合併 reviewer 會失去部分 context 多樣性：高風險保持分離，若 pilot 漏錯則縮小新預設適用面。
